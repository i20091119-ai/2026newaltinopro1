# 알티노 네오(Altino Neo) 통신 프로토콜 명세

> `altinoneoCodingplay.apk` (package `saeon.co.kr.altinoneocodingplay`, v1.3)를
> 리버스 엔지니어링해 복원한 프로토콜입니다. 실물 로봇으로 바이트 단위 검증은
> 하지 않았으므로, 최초 연결 시 아래 "검증 방법"으로 확인하세요.

## 1. 전송 계층 (매우 중요)

| 항목 | 값 |
|------|-----|
| 방식 | **Bluetooth Classic — RFCOMM / SPP** (BLE 아님) |
| SPP UUID | `00001101-0000-1000-8000-00805F9B34FB` |
| 앱이 여는 서버 소켓 이름 | `AltinoApp` |
| 권한 | `BLUETOOTH`, `BLUETOOTH_ADMIN` (BLE/위치 권한 없음) |
| 페어링 | OS의 일반 블루투스 페어링(SPP) 사용 후, 페어링된 기기 목록에서 선택 |

앱 전체 DEX를 검색했으나 `Gatt`, `BluetoothLeScanner`, WiFi/TCP/WebSocket
관련 코드는 **전혀 없습니다.** 순수 클래식 SPP 시리얼 링크입니다.

> ⚠️ **브라우저 Web Bluetooth API는 BLE(GATT)만 지원하고 클래식 SPP는 지원하지
> 않습니다.** 따라서 태블릿 브라우저만으로는 이 로봇에 직접 붙을 수 없습니다.
> 해결책은 최상위 `README.md`의 "아키텍처" 절 참고.

## 2. 송신 프레임 (앱 → 로봇), 고정 26바이트

앱은 26바이트 상태 버퍼(`sendBuf_byte`)를 유지하고, **50 ms 주기 타이머로 이
버퍼를 계속 전송**합니다(하트비트 스트리밍). 각 버튼/조작은 버퍼의 해당 바이트만
바꾸고, 실제 전송은 타이머가 담당합니다.

전송 직전 `ConnectedThread.Sendbyte()`가 헤더/체크섬/꼬리를 채웁니다.

| Index | 이름 | 값 / 의미 |
|------:|------|-----------|
| 0  | STX | `0x02` (고정) |
| 1  | CMD | `0x14` (=20, 고정) |
| 2  | CHECKSUM | `sum(bytes[3..24]) % 256` |
| 3  | const | `0x01` (고정) |
| 4  | const | `0x01` (고정) |
| 5  | STEERING | 조향 서보. **signed int8**, `-127..127` |
| 6  | MOTOR_A hi | 모터 A 16bit, big-endian (아래 인코딩 참고) |
| 7  | MOTOR_A lo | |
| 8  | MOTOR_B hi | 모터 B 16bit, big-endian |
| 9  | MOTOR_B lo | |
| 10 | DISPLAY/DOT | `0x00`=밝기모드(밝기=이 값), `0xFF`=도트매트릭스 비트맵 모드 |
| 11..18 | DOT ROWS | 8×8 도트매트릭스 행 비트맵 (mode=0xFF일 때) |
| 19 | SOUND | 부저/음계 코드 `0..255`, `0`=무음 |
| 20 | LED hi | LED 비트마스크 상위 바이트 |
| 21 | LED lo | LED 비트마스크 하위 바이트 |
| 22 | 0 | 미사용(체크섬에 포함) |
| 23 | 0 | 미사용 |
| 24 | 0 | 미사용 |
| 25 | ETX | `0x03` (고정) |

### 2.1 모터 값 인코딩 (`Go(a, b)`)

- `Go(a, b)`: 인자 `a` → MOTOR_B(bytes 8,9), 인자 `b` → MOTOR_A(bytes 6,7).
  (앱 내부 파라미터 순서 때문. 두 바퀴/구동 모터.)
- 값 범위는 `-1000..1000`으로 클램프.
- **양수 v**: `hi = v / 256`, `lo = v % 256` (그냥 16bit big-endian).
- **음수 v**: `raw = ~(|v|)` 를 16bit로 자른 값 = `0xFFFF - |v|`.
  즉 `hi = (raw>>8)&0xFF`, `lo = raw&0xFF`.
  예) `v=-300` → `raw=0xFED3` → `FE D3`. (2의 보수보다 1 작은 1의 보수 방식)

### 2.2 조향 (`Steering(v)`)

- `v` 를 `-127..127`로 클램프 후 **signed byte** 그대로 byte[5]에 저장.
- 좌회전 = `-127`, 우회전 = `127`, 직진 = `0`.

### 2.3 LED (`Led(v)`)

- 16bit 비트마스크. `byte20 = v/256`, `byte21 = v%256`.
- 앱에서 관측된 값: 전조등 `3`(0x0003), 후미등 `780`(0x030C),
  좌측 `160`(0x00A0), 우측 `80`(0x0050), `15`(0x000F), `0`=소등.

### 2.4 사운드 (`Sound(v)`)

- `0..255`. `0`=무음. 앱의 부저/피아노는 37~49 범위의 음계 코드를 사용.

### 2.5 도트매트릭스

- `Display(b)`: byte10=밝기(b), byte11~18=0 → 전체 밝기 제어(비트맵 지움).
- `DisplayLine(...)` / `Displayon(col,row)` / `Displayoff(col,row)`:
  byte10=`0xFF`로 두고 byte11~18의 각 비트를 켜고 끈다.
  `Displayon(col,row)`는 `byte[19-col] |= 1<<(row-1)` 형태 (col,row는 1..8).

### 2.6 송신 예시(테스트 벡터)

정지 프레임(모두 0):
```
02 14 02 01 01 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 03
```
전진 speed=300, 전조등 LED(3):
```
02 14 5F 01 01 00 01 2C 01 2C 00 00 00 00 00 00 00 00 00 00 00 03 00 00 00 03
```
(체크섬 `0x5F` = (1+1+1+44+1+44+3) % 256)

## 3. 수신 프레임 (로봇 → 앱), 고정 54바이트

앱은 1바이트씩 읽어 슬라이딩 윈도우로 프레임을 맞춘 뒤,
`[0]==0x02 && [1]==0x30('0') && [53]==0x03` 이면 유효 프레임으로 처리합니다.

| Index | 값 |
|------:|-----|
| 0 | STX `0x02` |
| 1 | `0x30` ('0') |
| 5..6  | IR1 (big-endian 16bit) |
| 7..8  | IR2 |
| 9..10 | IR3 |
| 11..12| IR4 |
| 13..14| IR5 |
| 15..16| IR6 |
| 47..48| CDS(조도 센서) |
| 49..50| BATTERY(배터리) |
| 53 | ETX `0x03` |

16bit 조합: `value = (hi<<8) | lo` (부호 없음).

## 4. 연결 및 스트리밍 절차

1. OS에서 알티노와 블루투스 페어링(SPP).
2. RFCOMM 소켓을 SPP UUID로 연결.
3. 연결 후 **20~50 ms 주기로 26바이트 상태 프레임을 계속 전송**.
   조작이 없어도 마지막 상태를 반복 전송(연결 유지 및 즉시 반응 목적).
4. 동시에 수신 스트림에서 54바이트 프레임을 파싱해 센서값 갱신.

## 5. 검증 방법

1. 이 웹앱(또는 브리지)로 로봇에 연결.
2. **정지 프레임**을 먼저 보내 안전 확인.
3. LED만 켜는 프레임(`Led(3)`)을 보내 링크/바이트 정렬 확인 — 눈으로 확인 가능.
4. 아주 낮은 속도(`Go(150,150)`)로 전/후진 → 모터 방향/인코딩 확인.
   방향이 반대면 MOTOR_A/B 매핑 또는 부호를 조정.
5. 수신 프레임에서 배터리/IR 값이 상식 범위인지 확인해 파싱 정렬 검증.
