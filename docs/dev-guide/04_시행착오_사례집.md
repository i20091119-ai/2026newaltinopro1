# 04. 시행착오 사례집 — 우리가 이미 밟은 지뢰들

형식: **증상 → 원인 → 해결(현재 규칙)**. 같은 지뢰를 다시 밟지 않기 위한 기록이다.
"규약이 왜 이렇게 까다롭지?" 싶을 때 이 문서를 보면 이유가 있다.
#1~17 은 2026-08, #18~ 은 2026-09 현장 운영·파일럿에서 나왔다.

**맨 먼저 읽을 것**: #20 · #21 · #37 — 코드가 아니라 **일하는 방식**에서 난 사고다.

## 통신 편

**1. 일부 로봇이 앱 스캔 목록에 안 뜸 (시스템 블루투스에는 보임)**
- 원인: 서비스 UUID 필터로 스캔했는데, 일부 로봇은 광고 패킷에 UUID를 안 실음.
- 해결: 필터 없이 스캔 후 이름 접두(ALTINO*)로 선별. → 네이티브에 반영 완료, JS는 신경 쓸 것 없음.

**2. 12대 동시 운영 중 절반이 연결 끊김**
- 원인 복합: LOW_LATENCY 스캔이 전파 점유 + 50ms(20Hz) 스트리밍 트래픽 + 재연결 5회 후 포기.
- 해결: BALANCED 스캔, **10Hz 고정**, 포기 없는 자동 재연결(2회부터 OS 배경 재연결). → **STREAM_MS=100 절대 유지.**

**3. 홈에서 연결했는데 다른 앱으로 이동하면 끊김/미승계**
- 원인: 앱이 진입 시 새로 connect()를 시도하거나 아무것도 안 함 (심화주차 앱에서 실제 발생).
- 해결: 모든 앱은 진입 시 `nativeStart()` — 살아있으면 adopt, 짝 있으면 그 로봇, 없으면 스캔.

**4. 학생이 옆 태블릿의 로봇에 연결해버림**
- 원인: 스캔 목록에서 아무 로봇이나 탭 가능했음.
- 해결: 1:1 짝 잠금 — 짝이 있으면 다른 로봇은 🔒 + 탭 무시, `🔓 짝 해제` 버튼으로만 변경.

**5. 연결 표시는 '연결됨'인데 로봇이 안 움직임**
- 원인: 반열림(좀비) GATT 링크 — OS가 끊김을 20초+ 동안 감지 못 함.
- 해결: 네이티브에 좀비 감지(송신 중 8초 무응답→강제 재연결) 내장. JS에서 할 일 없음.

**6. 연결 목록의 ⟨5DBA⟩가 로봇 스티커(BF16)와 달라 대혼란**
- 원인: MAC 뒤 4자리를 표시했는데 스티커는 BLE 이름 기반 번호였음.
- 해결: `stickerCode()`로 이름에서 번호 추출해 크게 표시. **MAC 전면 표시 금지.**

## 주행 편

**7. 코너에서 벽에 머리 박고 좌우로 와리가리**
- 원인 2중: (a) 임계값 조합이 잘못돼 '부드럽게 틀기' 분기가 죽은 코드였음 (b) 매 프레임 좌우 재판단 → 방향 뒤집힘 진동.
- 해결: 파생 임계값은 동적 계산(×0.55), 회피 방향은 **래치**해서 정면이 뚫릴 때까지 유지.
- 교훈: **방향 결정을 매 프레임 다시 하지 말 것.** 슬라이더 값이 바뀌면 파생 값도 따라 변하게.

**8. 측면을 긁으며 달리다 멈춤 — "측면 센서 고장?"**
- 원인: 센서는 정상. 감지 임계값(100)이 너무 낮아 코앞에서야 반응 → 보정이 늦음.
- 해결: 정면 감지를 높이고(당시 160 → 2026-09 파일럿에서 220 으로 다시 확정, #25), 측면 무효 시 전면 대각으로 폴백.
- 교훈: "센서 고장"으로 단정하기 전에 임계값을 의심. 진단용 **센서 점검 화면**(mode1 ⑥)을 활용.

**9. 코너에 대각만 끼었는데 후진을 안 함**
- 원인: 후진 판단이 전면 중앙(ir2)만 봄 — ir1=50인데 ir2=119라 안 걸림.
- 해결: 전면 3개 중 최솟값으로 판단 + 대각 끼임 임계 70 추가.

## 콘텐츠 편

**10. 도트매트릭스 숫자가 계속 깨져 보임 (⚠ 원격 오진 2회 — 꼭 읽을 것)**
- 증상: 처음엔 "14가 41로" 보이고, 자리를 고쳤더니 이번엔 글자 자체가 알아볼 수 없게 나옴.
- **진짜 원인**: `state.dotOn(col,row)`의 `row`가 **아래에서 위로 세는 번호**였다
  (`row 1` = 맨 아랫줄). `col`은 정상. 즉 **세로축만 뒤집혀** 있었다.
  그런데 기존 코드는 여기에 180° 회전(`dotOn(9-x, 9-y)`)을 얹어서 찍었고,
  → 세로는 우연히 상쇄되어 맞고 **가로만 거울상**이 됐다.
  그래서 "14"가 거울상이라 "41"처럼 보였고, 자리만 바꿔 고치니 글자 자체는
  여전히 거울상이라 계속 깨져 보였다.
- **해결**: `js/dotmatrix.js` — 논리좌표(x=왼→오, y=위→아래)로만 그리고
  마지막에 `dotOn(x, 9-y)` 로 한 번 변환. 자리 뒤바뀜은 구조적으로 소멸.
  기기 차이 대비로 8방향 보정화면(F 글자 보고 선택→저장) 제공.
- **오진 과정에서 배운 것**: 중간에 "배송문자 FONT를 바이트=행으로 읽으면 글자가 된다"는
  근거로 '축이 전치됐다'고 결론냈는데 **그것도 틀렸다**. FONT는 raw 바이트로 직접 쓰던
  경로라 우연히 그렇게 읽혔을 뿐이고, 실제 정답은 현장에서 보정화면을 돌려 확인됐다.
- **교훈**: ① `state.dotOn`을 직접 쓰지 말 것(반드시 `AltinoDot` 경유).
  ② 표시 문제를 좌표를 바꿔가며 "맞춰보는" 것은 거울/회전이 섞이면 반드시 실패한다.
  ③ **원격에서 사진만으로 두 번 틀렸으면 추측을 멈추고 현장에서 고를 수 있는 도구를 줄 것.**
  실제로 보정화면을 넣은 즉시 한 번에 정답(7번)이 나왔다.

**11. 답이 음수인 수학 문제 — 입력 불가**
- 원인: 숫자 키패드(inputmode=numeric)에는 마이너스가 없음.
- 해결: 문제은행 규칙 — **답은 항상 0 이상의 정수.** (문제 지문에는 음수 사용 가능)

**12. 연결 끊겨 앱 재시작 → 학생이 모은 점수·진행 증발, 대실망**
- 해결: 진행 상태를 저장(변경 시점마다 + 화면 이탈 시), 재시작 시 이어가기. 주제 앱은 `kit.store`.
  단, 오래된 저장(20분 넘음)은 다음 학생 것이 아니므로 이어가기를 띄우지 않는다(꼬리잡기).
- 교훈: **부스/교실 앱에서 진행 상태 저장은 선택이 아니라 필수.**

**13. 소리 안 꺼짐 / LED 잔류 / 멈췄는데 계속 달림**
- 원인: 프레임 스트리밍 구조상 마지막 상태가 유지됨.
- 해결: 지금은 kit 이 처리 — `kit.stop()`, `kit.beep`(자동 끔), 화면 이탈 즉시 정지(12 S1·S7).

**14. 센서 숫자가 덜덜 떨려 정신없음**
- 해결: UI 갱신 200ms 스로틀 + 고정폭 숫자칸(`tabular-nums`, `min-width`). 표준 패턴.

**15. 태블릿마다 화면이 잘리거나 스크롤 생김**
- 해결: 1280×800 가로 기준, `overflow:hidden` 레이아웃, 검증 스크립트에 오버플로 검사 포함.
- 교훈: 절대 위치·고정 픽셀 남발 금지, flex/grid로. 요소가 많으면 카드 내부만 스크롤.

## 운영 편 (앱 밖이지만 알아둘 것)

**16. "오케스트라 앱은 잘 됐는데" — 알고 보니 같은 BLE**
- 원본 오케스트라 앱을 리버스 엔지니어링해 같은 전송(ISSC UART)·같은 프레임을 확인.
  체감 차이는 재연결 전략 차이였고 지금은 동등. 통신 스택을 의심하기 전에 환경(아래)을 볼 것.

**17. 현장 끊김의 진짜 3대 원인**
- ① 로봇 배터리(<700) ② 2.4GHz 혼잡(태블릿 Wi-Fi는 5GHz로) ③ 거리/사람 차폐.
- 코드가 아니라 운영으로 잡는 문제. 학생 안내문에 반영해 둘 것.

## 일하는 방식 편 (2026-09) — 코드보다 먼저 읽을 것

**20. 코스 모양을 가정하고 고쳤다가 되돌림**
- 증상: "터널 안에서 배송 완료가 먼저 뜰 수 있다"고 보고 도착 판정을 '한 번 밝아진 뒤 다시 어두워질 것'으로 바꿨다.
- 원인: 코스에 **터널이 두 개(또는 같은 터널을 두 번)** 있다고 **가정**했다. 실제 코스는 n자, 터널은 끝에 하나뿐.
  그대로 갔으면 도착 판정이 영원히 안 걸려 **배송 활동이 통째로 실패**했다.
- 더 나쁜 점: 그 가정 위에 시뮬레이션을 짜고 "8/8 통과"라고 보고했다. **시뮬레이션이 검증한 건 코드가 아니라 가정**이었다.
- 교훈: **현장 조건(코스 모양·센서 유무·기기 지원)은 가정하지 말고 묻는다.** 시험이 내 가정을 담고 있지 않은지 본다.

**21. 감사 결과를 확인 없이 옮겼다가 틀림**
- 증상: "중2 일차함수 17문항은 2학기 내용"이라고 보고 → 실제로는 **중2 1학기 기말 범위**였다.
- 원인: 자동 감사(에이전트)의 판단을 근거 확인 없이 전달. 같은 감사에서 "초6 자명한 문제 22개"도 실제는 5개였다.
- 교훈: 남이(사람이든 도구든) 찾은 문제는 **원문을 직접 확인한 뒤** 전달·수정한다.

**37. 시험이 엉뚱한 걸 검증하고 있었다 (세 번)**
- ① 가짜 로봇 스텁이 **음수 모터값을 잘못 읽었다**(1의 보수를 2의 보수로 → −300 이 −301). 시험이 실패해서야 알았다(03 §9).
- ② #20 의 터널 시뮬레이션 — 틀린 코스 모델을 검증.
- ③ 몇 주 동안 만든 회귀 시험이 **개인 작업공간에만** 있다가 컨테이너 재시작에 전부 사라졌다.
- 해결: 시험은 **저장소에**(`tests/`). 그리고 **시험이 진짜로 잡는지**, 규칙을 일부러 깨뜨려 확인한다(`tests/mutation.mjs`, 12 문서).
- 교훈: "통과"는 시험이 맞을 때만 뜻이 있다.

## 안전 편 (2026-09) — 지금은 kit 이 막는다(12 문서)

**18. '정말 하시겠습니까?' 버튼이 태블릿에서 먹통**
- 원인: WebView 에 WebChromeClient 가 없으면 기본 `confirm()` 이 **창 없이 즉시 false**. 브라우저에선 멀쩡해서 몰랐다.
- 해결: 화면 안에 그리는 확인창(`js/ui.js` → `kit.confirm`). 기본 `confirm()`·`alert()` 금지(검사기가 잡음).

**19. 문제를 푸는 동안 차가 튀어나감** (12 S2)
- 증상: 에너지 0 → 차가 안 가니 아이가 패드를 계속 누른 채 → 충전소 문제를 품 → 에너지가 차는 순간 차가 출발.
- 원인: '게임 화면인가'만 봤다. 문제창·연결창·확인창은 게임 화면 **위에** 뜬다.
- 해결: 창이 보이면 움직임 0. 앱이 띄우는 창은 `kit.block(창)`.

**22. 홈으로 가도 로봇이 계속 달림** (12 S1)
- 원인: 화면을 벗어날 때 '움직임 의도'만 0 으로 하고 실제 정지 프레임은 **다음 100ms 틱**에 맡겼다.
  화면이 꺼지거나 페이지가 넘어가면 WebView 타이머가 멈춰 그 틱이 영영 안 온다. 로봇은 마지막 명령을 계속 실행.
- 해결: blur·pagehide·숨김에서 **그 자리에서** 정지 프레임을 보낸다.

**23. 정밀주차 전진·후진 버튼이 "잘 안 먹음"** (12 S3)
- 원인 넷: ① 패드가 `overflow:auto` 상자 안 → 손가락이 조금 움직이면 스크롤로 보고 터치 취소
  ② `touch-action:none` 없음 ③ 버튼 가장자리에서 미끄러지면 뗀 걸로 처리 ④ 그 화면만 20Hz 전송.
- 해결: `kit.hold`(포인터 캡처 + touch-action), 카드는 `overflow:hidden`, 10Hz.

**24. 속도 250 으로는 출발을 못 함** (12 S4)
- 원인: 모터가 제자리 정지 마찰을 못 이긴다. 달리던 중엔 250 으로도 굴러간다.
- 해결: 330 미만으로 **출발할 때만** 첫 180ms 를 400 으로(킥).

**27. 정지 직후 다시 출발하면 차가 제멋대로** (12 S5)
- 원인: 정지를 눌러도 옛 주행 루프는 `await sleep()` 안에서 자다가 곧 깬다. 그 사이 새 주행이 시작돼 있으면 **두 루프가 모터를 다퉜다.**
- 해결: 실행마다 세대 번호. 세대가 바뀐 루프는 스스로 물러난다 → `kit.run` 의 `r.alive()`·`r.sleep()`.

**28. 정지를 눌렀는데 차가 뒤로 한 번 튐**
- 원인: "조건이 될 때까지 달리기" 함수가 **정지로 중단된 것도 성공으로** 보고했다 → 다음 단계(후진 범프)가 실행됨.
- 해결: 중단은 실패로 보고, 기다린 뒤엔 항상 '아직 유효한가'를 본다 → `if (!await r.sleep(ms)) return;`

**29. 센서 신호가 끊겨도 25초를 직진** (12 S6)
- 원인: 센서 값은 마지막 것이 그대로 남는다. 끊겨도 '앞이 비었다'는 옛값을 믿고 달렸다.
- 해결: 자율 동작 중 1.2초 수신이 없으면 정지.

## 통신 편 (2026-09)

**26. 연결창을 한 번 열면 센서가 영구히 끊김**
- 증상: 화면엔 '연결됨'인데 잡힘 판정·배터리·센서 숫자가 전부 멈춤.
- 원인: 연결창이 만든 스캔용 객체가 **전역 콜백을 덮어써서** 게임 쪽 객체가 데이터를 못 받았다.
  덤으로, `scanning`·`error:busy` 같은 진행 알림까지 '연결 끊김'으로 처리해 스스로 재연결 고리를 만들었다.
- 해결: 데이터·상태는 연결을 '소유'한 객체 하나에게만, 스캔 결과만 모두에게. 확정 신호에만 연결 상태 변경(02 §9).

**30. 게임 화면이 가끔 멈칫함**
- 원인: 블루투스 쓰기(API 33+)는 결과를 기다리는 **동기 호출**인데, 그걸 웹 화면이 부른 스레드에서 **락을 쥔 채** 했다.
  스택이 밀리면 화면이 그만큼 얼었다(실측: 스택 300ms 지연 → 화면 302ms 정지, 3초 지연이면 메인 스레드도 977ms 정지).
- 해결: 큐에서 꺼내는 것만 락 안에서, 실제 호출은 전용 스레드에서. JVM 시험대로 확인(`tools/ble-test/`).

**31. 늦은 응답을 세어서 버리게 했더니 복구가 기어감 (되돌림)**
- 원인: 워치독이 건너뛴 명령의 늦은 응답을 '개수로 세어' 버리게 했다. 그런데 응답에는 우리가 붙인 번호가 없어서
  늦은 응답과 정상 응답을 **구별할 수 없다.** 로봇이 잠깐 멀어졌다 오면 그 수가 쌓여 **2초에 한 건씩만** 보냈다.
- 해결: 세기를 없앴다. 원래 피해(프레임 한 장을 스택이 버림)는 10Hz 로 곧 덮이니 사실상 무해. 더 나쁜 쪽을 피했다.

**35. 특정 차만 연결이 안 됨 (파일럿 "4번은 블루투스 연결이 안 됩니다")**
- 원인 후보: 그 태블릿이 **다른 차와 짝**이 되어 있거나, 짝지은 차가 꺼짐·배터리 부족·멀리 있음.
  화면엔 '재연결 중…'만 떠서 어느 쪽인지 알 수 없었다.
- 해결: 12초 넘게 재연결 중이면 **짝지은 차 번호와 푸는 법**을 알려 준다(kit 내장).

## 주행 · 현장 편 (2026-09 파일럿)

**25. 몇몇 차만 코너에서 '뱅글뱅글' — 차 고장이 아니라 기본값**
- 증상: 같은 코스에서 어떤 차는 잘 돌고 어떤 차는 제자리를 돈다. 강사들이 "튜닝 버튼 누르고 값 맞추니 됨".
- 원인: 보정값은 **태블릿에** 저장되는데, 예전엔 업데이트 때마다 **앱을 지우고 새로 깔아서** 맞춘 값이 날아가고
  기본값(정면 160·회전 127)으로 돌아갔다. 회전 127(최대)이면 정면 회피 때 너무 세게 꺾여 제자리를 돈다.
  사진 속 센서값을 대입해 재현: 정면 219 가 임계 220 바로 아래라 '회피 중'이 안 풀리고 계속 최대로 꺾였다.
- 해결: 강사들이 12대로 찾은 값(정면 220·좌 650·우 210·회전 57)을 **기본값**으로, '현장 기본값으로 되돌리기' 버튼,
  업데이트는 **덮어쓰기**로(앱 안 업데이트 버튼).
- 교훈: 태블릿에 저장되는 값은 **언젠가 날아간다** — 기본값 자체가 맞아야 한다.

**36. 9번 차는 뒤에 붙어도 잡힌 횟수가 안 올라감**
- 원인: 후면 센서 고장. 죽은 센서는 값이 **한 숫자에 붙박이**가 된다.
- 해결: 8초 동안 한 번도 안 변하면 '⚠ 후면 센서 무반응 — 차 교체'. 앱 문제인지 차 문제인지 바로 구분.

**38. 자리마다 조도가 달라 터널을 못 잡음 (파일럿 "첫 번째 자리 측정값 불안정")**
- 원인: 창가 자리는 빛이 세서 '밝은 곳'과 '터널 안'이 비슷하게 찍힌다. 그 사이값으로는 터널을 영영 못 잡는다.
- 해결: 측정 직후 두 값 차이가 120 미만이면 실제 두 값과 차이를 보여 주며 다시 재라고 경고.

## 콘텐츠 편 (2026-09)

**32. ÷4 를 '평균'이라고 불렀다**
- (620+88)÷4 = 177 은 두 값의 평균(354)이 아니다. 화면·활동지 모두 '사이값(평균)'이라 해서 **초등학생에게 평균을 잘못 가르칠** 뻔했다.
- 해결: ÷2 일 때만 '평균', ÷4 면 '터널 기준'으로 이름이 바뀐다. 활동지의 나누는 수는 빈칸.

**33. 문항 품질 — 정답은 맞았는데**
- 정답 930개는 독립 검산 0오류였지만: **조사 20곳**(0.7는→0.7은, x<11 를→11을), **학기 범위 밖·학년 간 중복**
  (중2 거듭제곱 5개가 중3 과 글자까지 똑같음), **답이 문제에 그대로 있는 문항**(1 : 8 = 1 : ?), **물건 수를 묻고 상자 수라 부름**.
- 해결: 문제은행 규칙(05 §5) + 검산 + 조사 검사. 분수 `a/b` 는 'b분의 a' 로 읽으니 **분자** 기준 받침.

**39. 활동지가 '한 장'이라더니 인쇄하면 두 장**
- 원인: 화면 폭 1280px 에서 높이를 쟀다. A4 인쇄 영역은 **188mm = 711px** 폭이라 글이 더 길게 접힌다.
- 해결: 인쇄 폭(711×971px)으로 재기. 문구 몇 줄 늘리면 2px 넘쳐 두 장이 되기도 한다(14 문서).

## 빌드 편 (2026-09)

**34. 앱 빌드가 조용히 실패 — 두 번**
- ① `versionCode (식).toInteger()` 를 Groovy 가 `versionCode(식)` 호출로 읽어 null 에 메서드를 부름 → 빌드 6번 연속 실패.
  그동안 "빌드 올라가는 중"이라고만 보고했다. → 빌드 번호는 android 블록 밖에서 변수로.
