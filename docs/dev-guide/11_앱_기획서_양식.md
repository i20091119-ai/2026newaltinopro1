# 11. 주제 앱 기획서 양식

> **코드보다 먼저 쓴다.** 한 장(이 양식)으로 수업 흐름·로봇이 하는 일·성공 판정을 정해 두면
> 15개 앱의 크기와 결이 맞고, 합칠 때 "이 앱은 왜 이렇게 다르지?"가 안 생긴다.

## 쓰는 법

1. `docs/topics/tNN.md` 를 연다 — 시간표 정보·하드웨어 조건·재사용 코드는 **미리 채워 두었다.**
2. **✎ 표시 칸**을 채운다. 다 채우면 `✎` 가 하나도 남지 않아야 한다(제출 검사기가 센다).
3. 다른 저자 1명에게 검토를 받고 상태를 `확정`으로 바꾼 뒤 코드를 시작한다.
4. 만들다가 바뀌면 기획서도 고친다 — 기획서와 앱이 다르면 강사용 자료(14)가 틀어진다.

## 양식

```markdown
# tNN 제목

> 상태: 초안 | 검토중 | 확정 · 저자: ✎ · 검토: ✎

## 1. 기본 정보
| 차시 | 반 | 연결 교과 | 로봇·센서 |

## 2. 배움 목표 — 이 앱을 마치면 학생이 할 수 있는 것 (1~3개, '~할 수 있다')
## 3. 수업 흐름 (차시별)
| 단계 | 분 | 학생이 하는 일 | 로봇이 하는 일 | 화면 |
## 4. 쓰는 하드웨어와 근거      ← 03 문서의 몇 절인지. 실측 안 된 값을 쓰면 '실측 계획'
## 5. 화면 흐름                ← 화면 이름과 넘어가는 조건
## 6. 성공 판정과 성장기록부    ← 무엇을 하면 성공인지 + kit.record.add 로 남길 문장·별점
## 7. 안전 점검 (12 문서)        ← 패드 / 자율 동작 / 창(모달) 있는지
## 8. 활동지                   ← 있으면 칸 목록 (14 문서 양식)
## 9. 재사용할 기존 코드
## 10. 열린 질문
```

## 칸별 요령

| 칸 | 잘 쓴 예 | 피할 것 |
|---|---|---|
| 2. 배움 목표 | "멈추는 거리가 속도에 따라 달라짐을 측정값으로 설명할 수 있다" | "로봇과 친해진다"(확인할 수 없음) |
| 3. 로봇이 하는 일 | "ir2 가 200 미만이면 kit.signal('success') 후 정지" | "알아서 멈춤" |
| 4. 근거 | "속도 300 순항 — 03 §1", "LED 비트 미실측 → 9차시 전 실측" | 값만 적고 출처 없음 |
| 6. 성공 판정 | "오차 10 이하 ⭐⭐⭐, 30 이하 ⭐⭐, 그 외 ⭐" | 별점 기준이 화면마다 다름 |
| 6. 성장기록부 | `title:'걸음마 시험 통과'` (12자 안팎, 학생이 읽을 말) | 내부 용어("t02 성공") |
| 7. 안전 | "패드 있음 → tests/t02.mjs 작성" | 빈칸 |

## 검토자가 보는 것 (5분)

- [ ] 2차시(80분) 안에 끝나는 분량인가 — 도입·정리 시간까지
- [ ] 로봇이 하는 일이 **03 문서에 있는 값**으로만 되어 있는가 (없으면 실측 계획이 있는가)
- [ ] 성공 판정이 숫자로 정해졌는가
- [ ] 다른 앱과 겹치는 활동이 없는가 (10 문서 §2)
- [ ] 신호(성공·실패 소리)를 kit.signal 로 쓰는가 — 직접 소리를 고르면 앱마다 달라진다
